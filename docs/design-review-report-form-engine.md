## 一、需求对齐度

### ✅ 已充分覆盖

| 需求编号 | 设计覆盖情况 |
|---------|------------|
| FD-01–FD-09（表单设计器） | 全覆盖：DesignerShell、Canvas、PropertyPanel、ConditionEditor、PreviewPanel、LockManager、ExportImport |
| WF-01–WF-02（审批链配置） | ApprovalChainConfig 支持组织架构/角色/指定人员三种审批人规则 |
| FF-01–FF-05（表单填写器） | FormCenter、FormFillPage、MyDrafts、MySubmissions、撤回流程 |
| AP-01–AP-05（审批操作） | 完整状态机：同意/拒绝/退回/转交 + 审批链时间线可见 |
| DM-01–DM-03（数据管理） | 数据列表查看、Excel 导出、统计接口 |
| CM-01–CM-02（通知、权限） | NotificationService + SSE，RBAC 自定义角色 |
| BR-01–BR-26（业务规则） | 核心规则均能追溯到设计元素 |

### ⚠️ 缺口与遗漏

**1. 模板审批流程 — 缺失**

需求规格中 BR-27（"表单模板提交审批"→ 通知审批人）和 BR-28（"表单模板审批通过/拒绝"→ 通知设计者）暗示**模板本身需要审批后才能发布**。但在设计中：
- 模板只有 `draft / published / archived` 三种状态，无审批中间态
- 通知类型枚举仅包含实例级事件（`instance_submitted`、`instance_approved` 等），无模板级通知
- 设计者可直接发布模板，无审批门槛

**建议**：明确模板是否需要审批流程。若需要，补充模板审批状态机；若不需要，在需求规格中标注该需求已移除并说明原因。

**2. 8 个开放问题未明确解决**

需求规格列出了 Q-01 至 Q-08，设计中做出了部分隐含假设但未显式决策：

| 问题 | 设计现状 | 风险 |
|------|---------|------|
| Q-01 通知渠道 | 仅假设 SSE + 站内通知，未涉及邮件/短信/企业微信 | 若后续需要多渠道，架构需返工 |
| Q-02 信息文本动静 | 作为纯展示组件处理，未支持可见性条件 | 若需动态显示则字段模型不兼容 |
| Q-03 子表单嵌套深度 | 设计了递归渲染但**未定义最大深度** | 存在无限递归或深层嵌套失控风险 |
| Q-04 人员选择器数据源 | UserPicker 组件存在但数据来源未指定 | 前后端接口无法对接到位 |
| Q-05 组织架构数据源 | 依赖 `User.manager_id` 和 `department_id`，但未说明组织树如何同步 | 审批人解析依赖未定义的外部系统 |
| Q-06 版本兼容策略 | 导入时校验版本但不兼容则拒绝——**未定义兼容矩阵** | 向前/向后兼容策略空白 |
| Q-07 草稿自动保存策略 | `PUT /api/instances/:id/values` 接口存在但触发策略未定 | 防抖间隔？失焦触发？定时轮询？ |
| Q-08 离线填写能力 | **完全未提及** | 移动端核心场景缺少方案 |

**3. 草稿与模板版本不匹配**

产品规格定义了边缘场景："草稿对应的表单模板已更新"。设计通过 `template_snapshot` 解决了实例的版本隔离，但草稿仅有 `template_id` 和 `field_values`——当模板 Schema 变更（增删字段、修改验证规则），已存草稿的数据映射到新结构时会丢失或错位。

**建议**：草稿打开时对比 `template.updatedAt` 与 `draft.updatedAt`，出现差异时警告用户并基于字段 ID 尽力映射已有数据。

**4. 字段标签唯一性校验缺失**

产品规格 BR-F1-05 要求："字段标签在同一个表单模板内应保持唯一（警告而非阻断）"。该规则在 SchemaParser 和模板保存 API 中均未体现。

**5. 提交时未校验模板下线状态**

产品规格边缘场景："用户提交时模板已被下线"。设计中的提交接口未检查 `template.status === 'published'`——即使模板已被下线，用户仍可提交。

## 二、复杂度评估

### 需关注的高复杂度点

**1. 可视化条件编辑器 — 风险最高**

嵌套 AND/OR 条件 AST 的可视化编辑器是整个系统中最复杂的单一组件。设计用寥寥数段描述，但该组件可能消耗前端开发总量的 30–40%。ConditionEvaluator 的 AST 设计干净，但**面向零代码用户的编辑器 UI 是真正的难点**。

**建议**：MVP 阶段简化为单层 AND 条件（不嵌套、不支持 OR），完整的 AST 编辑器推迟至 Phase 2。

**2. 状态管理方案碎片化**

设计提出三种并行的状态管理方案：
- React Context + useReducer（表单实例、设计器画布）
- Zustand（全局状态）
- 自定义 hook + fetch（服务端缓存）

三种方案并存会让团队困惑"状态该放哪里"。MVP 阶段用 Context + useReducer 统一所有层级即可。

**3. SSE 实现复杂度被低估**

SSE 协议确实比 WebSocket 简单，但周边基础设施（连接管理、断线重连、事件回放、多实例扩展）并不简单。对于 50 并发用户、日均 100 次提交的规模，**30 秒轮询更简单且完全够用**。

### 合理的复杂度

- Component Registry + Factory 模式：扩展性刚需，标准做法
- 审批状态机：必要复杂度，建模质量好
- Schema 快照隔离：正确且必要的复杂度

## 三、可维护性

### 优势

- **Component Registry** 使新增字段类型无需修改引擎代码
- **Schema 驱动**令表单行为变更无需部署
- 后端服务划分清晰，职责单一
- FormEngine（共享层）与 Designer/Filler（消费者）的边界分明

### 风险项

**1. 缺少 API 版本策略**

REST 端点未包含版本前缀（如 `/api/v1/...`）。API 演进时客户端会直接崩溃。**趁现在零成本，立即加上 `/api/v1/`。**

**2. JSONB Schema 演进无迁移路径**

Schema JSONB 结构（字段类型、验证规则、条件 AST）必然迭代。当格式变化时：
- 数据库中已有模板是旧格式
- 引擎必须支持多版本解析或迁移数据
- 两种策略均未定义

**建议**：在每个存储的 Schema 根部加入 `schemaVersion` 字段，定义引擎对未知版本的处理策略（拒绝/警告/自动迁移）。

**3. ConditionEditor ↔ ConditionEvaluator 紧耦合**

AST 格式是可视化编辑器和求值引擎之间的唯一契约。任何 AST 变更同时影响两端。**应将 AST 类型定义为独立的共享模块并显式版本化。**

**4. 同构校验代码的约束未声明**

设计正确识别了前后端共享校验逻辑的需求，但未声明关键约束：共享代码必须是纯函数，不能依赖 DOM、浏览器 API 或 Node.js 专有模块。缺少该约束会导致运行时错误。

**5. 响应式断点单一**

仅提到 768px 作为移动端分界点，未覆盖平板和宽屏场景。建议预设断点体系（320/768/1024/1440）。

## 四、安全性

### 已充分覆盖

| 维度 | 设计措施 |
|------|---------|
| 认证 | JWT Bearer Token |
| 授权 | 权限中间件，角色-权限非硬编码 |
| 服务端校验 | 明确"不信任前端校验"，全量重验 |
| 文件安全 | MIME 类型校验、大小限制 |
| XSS | 提及对 label/选项进行转义 |
| 配置注入 | 导入 JSON 时校验结构合法性 |
| 签出锁 | 服务端校验锁归属 |

### 缺口

**1. CSRF 防护 — 缺失**

若 JWT 存储在 Cookie 中（即使是 `httpOnly`），API 仍面临 CSRF 风险。设计未指定 Token 存储位置及防护策略。

**建议**：明确 Token 存储方案——推荐 `httpOnly` Cookie + CSRF Token Header，或 `Authorization` Header + localStorage 并显式接受 XSS 风险。

**2. 速率限制 — 缺失**

未对任何接口做速率限制。高风险接口：登录、文件上传、表单提交、Excel 导出。`GET /api/data/export` 可被利用发起 DoS 攻击。

**3. 文件上传路径穿越 — 缺失**

FileService 校验了文件类型和大小，但未对文件名做路径消毒。恶意文件名（如 `../../../etc/passwd`）可能导致路径穿越。

**4. 审批意见可见性粒度过粗**

设计规定审批链上所有参与者均可互看审批意见。对于 HR 等敏感场景，某审批人对提交人的意见可能不适合对其他审批人公开。

**建议**：增加 `commentVisibility` 字段：`all_participants` | `submitter_only`。

**5. 数据导出审计追踪缺失**

Excel 导出（含敏感表单数据）应生成审计日志，记录谁在何时导出了什么数据、应用了什么筛选条件。当前仅笼统提及"关键操作记录"。

**6. CORS 配置 — 缺失**

SPA 可能与 API 不同源部署，CORS 策略需显式定义，不应留待部署时处理。

## 五、可靠性

### 优势

- 模板快照模式确保运行中实例不受模板变更影响
- 审批状态机阻止非法转换
- 签出锁提供强一致性编辑保护
- 审批人解析失败时优雅降级（进入异常状态、通知管理员）

### 问题

**1. 未定义事务边界 — ⚠️ 最关键**

以下操作涉及多次写入，必须保证原子性：

| 操作 | 需原子化的写入 |
|------|-------------|
| 表单提交 | 创建实例 + 快照模板 + 创建审批记录 + 发送通知 |
| 审批操作 | 更新审批记录 + 推进/终止实例 + 创建下一节点记录 + 发送通知 |
| 模板发布 | 更新状态 + 清理缓存 |

**设计未指定使用数据库事务还是补偿操作（Saga）。这是整个设计中最关键的可靠性缺口。**

**2. 缺少幂等键**

网络重试 `POST /api/instances/:id/submit` 或 `POST /api/approvals/:id/approve` 可能导致重复提交或重复审批。

**建议**：所有写操作接口要求 `Idempotency-Key` Header，并文档化幂等窗口（如 24 小时）。

**3. 撤回与审批的竞态条件**

撤回条件（"审批人尚未处理"）与审批操作之间存在经典的 TOCTOU 竞态窗口——审批人点击"同意"的同时提交人点击"撤回"，两个检查同时通过。

**建议**：对 FormInstance 增加 `version` 列做乐观锁，或对两个操作加悲观锁。

**4. SSE 事件回放缺失**

设计提到 SSE 断线自动重连，但未指定重连期间丢失的事件是否回放。若用户断连 2 分钟错过审批更新，重连后将看到过期状态。

**建议**：基于 Last-Event-ID 实现事件回放，或提供轮询回退机制。

**5. 通知投递保证级别不明确**

通知创建是 `INSERT notification` + SSE Push。如果 INSERT 成功后服务器崩溃，通知在数据库存在但用户未收到实时提醒。这是可接受的（下次加载时通知中心会显示），但应承认**实时通道是 at-most-once 投递**。

**6. 异步 Excel 导出失败处理**

设计对超过 1000 条的导出采用异步生成。若异步任务失败（OOM / 超时），用户如何获知？通知系统需支持失败通知而非仅成功。

**7. 数据库连接韧性缺失**

未提及连接池配置、重试逻辑或熔断策略。至少应声明预期使用连接池并定义瞬态错误的默认重试策略。

## 六、测试策略

### 优势

- 测试金字塔方向正确（单元多、E2E 少）
- 单元测试覆盖所有核心引擎模块
- 集成测试覆盖关键状态转换
- E2E 定义了 4 条关键用户旅程

### 缺口

**1. 无性能/负载测试**

NFR 要求 50 并发的在线填写者、日均 100 次提交。目标不大，但仍需验证。无负载测试计划。

**2. 无可访问性测试**

目标用户为企业内部员工，但 WCAG 2.1 AA 可访问性依然重要。设计器的拖拽交互尤其具有可访问性挑战。

**3. 无视觉回归测试**

表单渲染器的核心价值是视觉一致性。截图对比式的视觉回归测试能捕获单元测试遗漏的渲染问题。

**4. 审批状态机 — 需要基于属性的测试**

审批状态机有 7 个状态、6 种转换、多种角色。独立测试单个转换无法发现转换序列中的错误。基于属性的测试（生成随机合法/非法转换序列，验证不变量）更全面。

**5. 跨浏览器测试范围**

拖拽式设计器和移动端响应式需要显式的跨浏览器测试目标。最低要求：Chrome、Edge、Safari、Mobile Safari、Mobile Chrome。

## 七、缺失的跨领域决策

## 九、整改建议

1. **定义事务边界**：为提交、审批操作、发布操作明确事务或补偿策略（数据库事务 vs Saga）。

2. **增加幂等键**：所有写操作接口要求 `Idempotency-Key` Header，文档化幂等窗口（建议 24 小时）。

3. **增加乐观锁**：对 `FormInstance` 和 `FormTemplate` 增加 `version` 列，防止撤回-审批竞态和并发保存冲突。

4. **解决 BR-27/BR-28 去留**：明确模板是否需要审批才能发布。若是，补充模板审批状态机；若否，在需求规格中标注移除原因。

5. **关闭 8 个开放问题**：在开发启动前至少明确：通知渠道、子表单最大深度、人员选择器数据源、组织架构数据源、版本兼容策略、草稿自动保存触发策略。

6. **Schema 增加版本号**：在 JSONB Schema 根部加入 `schemaVersion` 字段，定义引擎对未知版本的处理策略。

7. **API 增加版本前缀**：所有路由使用 `/api/v1/...` 格式。

8. **草稿增加版本检查**：打开草稿时比较模板更新时间，若模板更新则警告用户，基于字段 ID 尽力映射已有数据。

9. **提交接口增加模板状态校验**：提交时必须确认 `template.status === 'published'`。

10. **明确 JWT 存储与 CSRF 策略**：推荐 `httpOnly` Cookie + CSRF Token 方案。

11. **增加速率限制**：在登录、文件上传、提交、导出接口上实施。

12. **上传文件名消毒**：防止路径穿越攻击。

13. **简化 MVP 状态管理**：统一使用 Context + useReducer，确有需要时再引入 Zustand。

14. **在设计中定义标准化 API 错误格式和分页封包**。

## 十、设计亮点

- **Schema 驱动架构**是正确的选择——关注点分离、单一事实来源、天然适配问题域
- **Component Registry 模式**设计良好，提供了真正的可扩展性
- **模板快照隔离**正确解决了"模板变更 vs 运行中实例"问题
- **审批状态机**建模全面，正确覆盖了所有必需的转换
- **服务端重验**被明确强调——对配置驱动系统至关重要
- **权限模型**灵活（RBAC 自定义角色），正确分离了数据隔离规则与功能权限
- **技术选型务实**——Vite、Express、PostgreSQL、JSONB 是充分论证的"无聊技术"，与系统规模匹配
- **测试策略**覆盖了正确层次，仅需在几个方面补充

---

## 十一、最终评定

### 评级：**需修订（Needs Revision）**

设计在核心架构层面是合理的——Schema 驱动、Component Registry、模板快照隔离都是正确的选择。但在当前状态下无法进入实施，原因如下：

1. **严重的可靠性缺口**（无事务边界、无幂等性）在投产前就会表现为数据损坏 Bug
2. **一项显式需求疑似被遗漏**（模板审批流程），无合理解释
3. **需求阶段的 8 个开放问题悬而未决**，其中多项实质性影响数据模型和 API 设计
4. **10 项跨领域架构决策**（部署、可观测性、后台任务、迁移工具）未文档化

### 建议推进路径

| 阶段 | 处理内容 | 时间节点 |
|------|---------|---------|
| 立即 | 解决严重 + 高严重度问题（C1–C4） | 实施启动前必须完成 |
| Phase 1 MVP 前 | 解决中严重度问题（C5–C14） | 编码启动前完成 |
| Phase 2 | 低严重度问题（C15–C16） | 可延期处理 |

**预计额外设计工作量**：2–3 天，用于关闭上述识别的缺口。
