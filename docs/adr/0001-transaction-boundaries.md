# ADR-0001：混合事务策略——数据库事务 + 异步通知

> 日期：2026-08-12
> 状态：已采纳
> 关联问题：设计评审 C1（严重）

---

## 背景

表单提交和审批操作涉及多次写入（实例创建、快照、审批记录、通知）。设计阶段未指定如何保证这些写操作的原子性。若不加控制，部分写入成功、部分失败会导致系统进入非法状态——例如 Instance 已创建但 ApprovalRecord 缺失，表单永远卡在"未审批"状态。

## 决策

采用**混合策略**：

```
数据库事务内（原子）：
  1. INSERT FormInstance
  2. INSERT template_snapshot
  3. INSERT ApprovalRecord（含审批人解析）

数据库事务外（异步，事务提交后触发）：
  4. INSERT Notification
  5. SSE push（实时推送）
```

### 关键规则

1. **审批人解析在事务内执行**。若解析失败（如直属上级不存在），整个事务回滚，提交失败，前端报错："审批流程配置异常，请联系管理员"。
2. **Notification 持久化在事务后执行**。若事务成功但通知写入失败，通知中心在用户下次加载时仍可展示（通过查询 Instance/ApprovalRecord 状态反推缺失事件）。
3. **SSE push 是 at-most-once**。接受推送丢失——用户在通知中心能看到持久化的通知。

## 替代方案

### A：纯数据库事务（全包）

将所有 5 步放入一个 ACID 事务。**拒绝原因**：SSE push 无法回滚——push 出去了就是出去了，没有"撤回推送"的操作。且长事务持有锁影响并发。

### B：Saga / 补偿事务

每步独立提交，失败时执行补偿操作。**拒绝原因**：补偿逻辑复杂度高（如补偿"审批已通过"的通知要发什么？），且本系统的写入链不长，DB 事务完全能覆盖核心路径。过度设计。

### C：无事务

每步独立执行，失败时留下不一致数据，靠后台修复任务处理。**拒绝原因**：不可接受——提交是核心业务操作，数据不一致会直接影响用户。

## 后果

- **正面**：核心数据（Instance + Snapshot + ApprovalRecord）强一致，不会出现"有实例无审批"或"有审批无实例"
- **正面**：通知与核心写入解耦，失败不阻塞用户操作
- **负面**：SSE push 可能丢失，用户需依赖通知中心轮询获取最新状态（可接受——通知中心是数据源，SSE 是加速通道）
- **负面**：审批人解析失败导致整个提交回滚，用户体验不够友好——但好过提交后卡在异常状态
