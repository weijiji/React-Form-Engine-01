# ADR-0010：权限码驱动的访问模型 —— 取代门户路由模型

> 日期：2026-08-14
> 状态：已采纳（取代 ADR-0009）
> 关联：工单 18（权限码门禁）→ 本 ADR 移除门户概念

---

## 背景

ADR-0009 把「5 个角色门户」做成第一等的路由概念：`/designer /filler /approver /admin /ops` 各自带一个 `PortalShell`、一套导航分区、门户切换器、门户落点（`primaryPortal`）、以及 shared 里的 `PORTALS` 目录（门户 → 解锁权限码的捆绑表）。工单 18 已把登录后的**门禁**从角色名换成权限码，但门户这个组织单元本身还在——它是角色名硬编码问题的根源：

- 导航被门户切碎：同一份侧边栏无法跨域组合，混合权限用户（如设计者 + 管理员）只能看到其中一栏。
- 切换器按门户呈现：把「权限码集合」降维成「一个门户」，丢失了真实权限粒度。
- 落地按门户优先级：`primaryPortal` 基于角色名推导，而非用户实际持有的权限码。
- shared 存了一张「门户 ↔ 解锁码」捆绑表：导航、路由守卫、落地读它，等于把角色捆绑重新引入。

现场实测暴露的三类问题皆源于此（管理员持全部码只见 admin 门户、设计者+管理员重新登录丢设计者访问、admin 角色可被删除后系统失守）。判定：门户模型是错误决策，移除它，让**权限码成为访问的唯一事实来源**。

## 决策

1. **移除门户概念**：无 `PORTALS` 目录、无 `PortalShell`、无门户切换器、无 `primaryPortal`、无门户品牌副标题/面包屑。shared 不再导出任何门户相关代码。
2. **URL 前缀保留，仅作纯路径组织**：`/designer /filler /approver /admin /ops` 继续存在，但只是分组路径，**没有任何门禁含义**，也不代表身份。**不拍平 URL**（用户确认）。
3. **一份统一侧边栏 `APP_NAV`**，按域分组（系统管理 → 设计工作台 → 表单 → 审批 → 运维 → 通用），按用户 `permissions` 过滤。管理员看到全部组；混合权限用户看到混合侧边栏（预期）。
4. **页面级门禁**：每个页面用自己所需的权限码门禁（如「我的模板」=`template:edit`、「创建表单」=`template:create`、「用户管理」=`admin:manage_users`）。**`ROUTE_CODES[path]` 是导航项与路由守卫共同读取的唯一事实来源**，永不漂移。同一条明细路由显式继承其列表页的码（如 `/designer/templates/:id` 继承 `template:edit`）。
5. **根路径 `/` 落地 = 权限解锁的第一个导航项**（`firstAccessiblePath`）。「通知中心」无码恒可访问，因此任意登录用户必有落点；`/403` 仅为 `APP_NAV` 为空时的防御分支。
6. **一个 Shell、一个登录页**：`AuthenticatedShell` 读取 `useAuth`，把 `APP_NAV` 过滤后交给纯展示的 `Shell`。设计器全屏工作台 `/designer/templates/:id` 仍在 Shell 之外（三栏无侧栏），但以 `template:edit` 门禁。
7. **访问决定只看 `user.permissions`**，从不看角色名或门户成员关系。

### 落地示例（五个种子角色的真实结果）

`APP_NAV` 组序 + 页面级码 + 种子权限码共同决定落地：

| 角色 | 种子权限码（要点） | 首个解锁导航项 | 落地 |
|------|--------------------|----------------|------|
| 管理员 | 全部 20 码 | 系统管理 → 用户管理 | `/admin/users` |
| 设计者 | 含 `template:publish` | 系统管理 → 模板管理 | `/admin/templates` |
| 填写者 | `form:fill` 等 | 表单 → 表单中心 | `/filler/forms` |
| 审批者 | `approval:view_pending` 等 | 审批 → 待审批 | `/approver/pending` |
| 运维 | 含 `data:view` | 系统管理 → 数据管理 | `/admin/data` |

设计者持 `template:publish`（→ `/admin/templates`）、运维持 `data:view`（→ `/admin/data`），因此二者落在系统管理组的页面——这是**纯页面级门禁 + 现有种子码的算术必然**，也是「混合侧边栏（预期）」的直接体现。若希望各角色干净地落在各自域（设计者 → `/designer/templates`），需调整种子权限码（如设计者不含 `template:publish`），属权限模型变更，不在本 ADR 范围。

## 替代方案

- **保留门户模型，仅把门禁换码**（工单 18 的中间态）：拒绝。门户仍切碎导航、按门户呈现切换器、按角色名推落地，角色名硬编码的根因未除。
- **拍平 URL（单一前缀）**：拒绝（用户确认保留前缀作纯组织）。前缀分组对运维/审计/书签友好，且没有门禁负担。
- **区域级门禁（门户 → 解锁码捆绑）**：拒绝（用户确认页面级）。捆绑表让「设计者+管理员」这类组合用户必须持有区域并集，粒度粗，且重新引入角色捆绑。
- **落地按域名先序排列 `APP_NAV`**：拒绝。单一组序无法同时满足「管理员落 `/admin/users`」与「设计者落 `/designer/templates`」（设计者持 `template:publish` 会先解锁系统管理的模板管理）；以管理员为主要账户、保持系统管理组在首。

## 后果

- **正面**：权限码成为唯一事实来源，客户端零角色名/门户硬编码；导航与路由守卫读同一张 `ROUTE_CODES` 表，永不漂移；新增页面只需补一行码 + 一个路由对象。
- **正面**：混合权限用户获得真实、可组合的侧边栏与落地；设计者+管理员不再互相遮蔽。
- **负面**：混合侧边栏是预期结果（见上表），设计者/运维会看到系统管理组的个别页面；这是纯页面级门禁的代价，接受。
- **负面**：删除 `PORTALS` 目录与门户测试是一次性代码清理；未来读者困惑「为何无门户」——本 ADR 记录原因。
- **服务端**：路由/鉴权中间件本就按权限码校验，不受本改动影响；接口层按码鉴权属后续工单。
