# ADR-0006：MVP 阶段条件编辑器范围

> 日期：2026-08-12
> 状态：已采纳
> 关联问题：设计评审 C10（中）

---

## 背景

设计评审报告将可视化条件编辑器标记为"整个系统中最复杂的单一组件"，可能消耗前端开发总量的 30-40%。该组件需要将嵌套 AND/OR 条件 AST 转化为零代码用户可理解和编辑的 UI——单这一项的 UX 设计复杂性就超过表单引擎其他组件之和。

完整需求（设计规格 §2.2.3）要求的 UI 包括：
- 逐层构建 AND/OR 组合条件
- 条件行内联添加/删除/重新排序
- 依赖字段下拉选择、运算符选择器、比较值输入
- 嵌套组的缩进和视觉分层

## 决策

**MVP 仅支持单层 AND 条件，不支持嵌套 OR 和分组嵌套。**

### MVP 支持

```
[ 设备类型 ▼ ]  [ 等于 ▼ ]  [ 研发设备 ▼ ]      [×]
[ 是否涉密 ▼ ]  [ 等于 ▼ ]  [ 是 ▼ ]            [×]
                                              [+ 添加条件]
```

- 所有条件之间是 **AND** 关系（所有条件同时满足）
- 条件编辑器 UI：平铺的行列表，每行一个条件
- ConditionEvaluator 仅求值 AND 组合——AST 无 OrCondition 节点

### Phase 2 增加

- 条件行支持 AND/OR 切换按钮
- 条件行下可插入嵌套组（递归嵌套条件编辑器）
- 分组缩进和括号可视化
- ConditionEvaluator 支持完整 AND/OR AST

### 数据格式兼容性

MVP 存储的 Schema 中，`visibilityCondition` 格式为简单的条件数组（隐式 AND）。Phase 2 升级时：
- 旧条件格式（`Condition[]`）视为顶层 AND 节点
- 迁移脚本将旧格式自动包装为 `AndCondition { conditions: [...] }`

```json
// MVP 格式（Phase 1）
"visibilityCondition": {
  "conditions": [
    { "fieldId": "fld-device-type", "operator": "equals", "value": "rd" },
    { "fieldId": "fld-is-classified", "operator": "equals", "value": true }
  ]
}

// 升级后格式（Phase 2）
"visibilityCondition": {
  "type": "and",
  "conditions": [...]
}
```

## 替代方案

### MVP 直接做完整 AST

**拒绝原因**：条件编辑器的核心难题不是 AST 求值（纯逻辑，简单），而是**让零代码用户能理解嵌套布尔表达式**。这个 UX 问题没有已知的好方案——需要原型迭代。把 MVP 卡在这个组件上不值得，且 90% 的业务场景仅需单层 AND。

### MVP 不提供条件编辑器，用 JSON 编辑器代替

让设计者手写 JSON 条件。**拒绝原因**：这一刀砍到骨头上——字段联动是整个产品的核心差异化能力。没有可视化条件编辑器，这个产品只是一个"表单布局工具"，竞争力大打折扣。

## 后果

- **正面**：条件编辑器可在 2-3 天完成（vs 完整版本的 2-3 周），MVP 快速出街
- **正面**：数据格式上有明确升级路径，不产生技术债
- **负面**：Phase 2 需要重新设计条件编辑器 UI——但这是有意为之，因为 Phase 1 使用反馈会指导 Phase 2 的 UX 方向
- **负面**：不支持 OR 条件意味着像"设备类型 = 研发 OR 设备类型 = 生产"这样简单的场景也需要拆成两条独立规则——用户体验有折损
