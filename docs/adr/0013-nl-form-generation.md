# ADR-0013：NL 表单生成 —— 简化建议结构 + 确定性翻译 + 规则兜底

> 日期：2026-08-20
> 状态：已采纳
> 关联：工单 21（NL 对话创建表单）；CONTEXT.md「NL 创建」；UX 设计规格 §4.2；sitemap `/designer/create/nl`

---

## 背景

「自然语言创建」（`/designer/create/nl`，现为占位页）让设计者像聊天一样描述表单需求，AI 生成结构建议，用户确认后跳入设计器微调。这是设计器的**入口替代方案**，核心价值是「用户不需要理解字段类型」（UX §4.2）。

实现前有三个根本问题需要定论：

1. **AI 后端从哪来** —— 代码库此前没有任何大模型集成；原型的「AI」只是 4 个硬编码示例 + 关键词匹配。
2. **AI 输出什么** —— 直接产出引擎 schema，还是产出中间结构？引擎 schema 要求 `schemaVersion` + 章节 + 字段 id + 13 种字段类型 + 验证规则，让 LLM 一次生成完全合法的一次通过率低，且用户预览时看到的是一堆 JSON，无法直接理解或编辑。
3. **不可靠时的行为** —— LLM 输出可能非法、无 key 时不可用、长尾描述可能谁都不匹配。

## 决策

### 1. LLM 为主，本地规则引擎兜底

服务端调 Claude API（Anthropic Messages API，默认 Haiku 4.5）生成建议；**无 `ANTHROPIC_API_KEY`、调用失败、或输出无法归一化时，回退到本地规则引擎**（6 个预置示例：请假/采购/设备报备/报销/出差/入职，按关键词匹配，与 UX 规格 §4.2 对齐）。规则引擎也命中不了时，客户端展示明确错误并引导用户换说法或点快捷示例——不模糊匹配、不返回无价值的空结构。

### 2. AI 输出「表单结构建议」而非 schema

新增领域概念 **FormStructureSuggestion（表单结构建议）**（CONTEXT.md）：AI 输出、用户预览编辑、服务端翻译三方共用的中间结构，仅含：

```
{ name, description?, sections: [{ title, fields: [{ label, type, required, options? }] }] }
```

- `type` 为受限枚举（text/textarea/number/select/radio/checkbox/date/datetime/file/user-picker），LLM 从白名单选 token，翻译时未识别一律落为 `text`。
- `options` 仅 select/radio/checkbox 使用。
- **不含审批链**（审批是设计器里的一步，UX 旅程本就默认推荐「直属上级」；审批人解析是 `ApprovalResolver` 的复杂领域，不该被 NL 简化绕过）；**不含分类**（`category` 直接落 `null`，用户在设计器补充）。

### 3. 确定性翻译器落引擎 schema，SchemaParser 兜底

建议结构经**确定性代码**翻译为完整 schema（补 `schemaVersion: "1.0.0"`、章节/字段 id、把 `options` 转 `{label,value}`），再经 `SchemaParser` 校验兜底。翻译器与归一化器都是纯函数，放在 `shared/`（零运行时依赖，vitest 直测）；客户端在确认时调用它，把翻译后的 schema 交给既有的 `POST /api/v1/templates`（复用创建 + 自动签出流，不新建翻译端点）。

### 4. 单轮生成 + 追加修正，服务端无状态

首次描述 → 生成建议；之后用户可继续发消息（「去掉附件、加上到货日期」），客户端把**当前建议 + 新消息**发给 `refine`，AI 出修正版。服务端不持久化会话，刷新即重新开始——对「创建模板」这种一次性流程可接受，符合 REST 无状态风格。

### 5. 确认 = 复用模板创建流

用户确认后 `POST /api/v1/templates`（`{name, description, category: null, schema: 翻译后}`），自动签出，跳转 `/designer/templates/:id`。**不提供「存为草稿」按钮**——`FormTemplate` 创建后本就是 `draft` 状态，该按钮与「进入设计器」在模板状态上等价，属冗余。预览卡只有「创建并进入设计器」与「继续修改」两个动作。

## 替代方案

- **AI 直接输出完整 schema JSON**：拒绝。一次通过率低需重试/修复循环；预览不可读不可改；把 AI 不可靠的部分交给重试，不如交给确定性翻译。
- **纯本地规则（原型式）**：拒绝。严格说不是 AI，长尾描述无法处理；「由 AI 给出表单建议」是明确的产品诉求。
- **完整多轮对话（AI 主动反问、上下文会话）**：推迟。需会话状态/上下文管理，复杂度与成本显著上升，MVP 收益不足。
- **生成结果含审批链**：拒绝。审批人解析是本项目最复杂领域之一，NL 生成绕过设计器的确认步骤是帮倒忙（UX 旅程本就安排设计器内配置审批人）。
- **失败时模糊匹配最近示例 / 返回空结构**：拒绝。误导性大于帮助 / 产出无价值，明确错误 + 引导更诚实。

## 后果

- **正面**：AI 不可靠的部分由确定性代码兜底，翻译结果必然合法；`shared/` 纯函数可无 DB/DOM/网络直测（一级 seam）；无 key 时功能降级不中断（与 server 降级模式一致）。
- **正面**：用户预览看到的是人话字段清单，可改标签/必填/删除/加字段，无需理解字段类型（UX 原则）。
- **正面**：两个新端点 `POST /api/v1/nl/generate`、`POST /api/v1/nl/refine` 挂在 `template:create` 权限下，走统一 auth/CSRF/错误包装。
- **负面**：引入外部依赖与成本（Anthropic API key、调用成本），但规则兜底保证功能永在线；LLM 输出仅影响生成的字段内容，无指令执行面（prompt injection 不构成安全边界突破）。
- **负面**：新增一组 `shared/` 纯函数与两个端点需测试覆盖；后续若要完整多轮或审批链，是增量扩展而非重构。
