# UX Review Report：动态表单引擎

> 评审日期：2026-08-05
> 评审对象：[UX 设计规格说明书 v1.0](ux-design-spec-form-engine.md)
> 评审框架：10 维度 UX 评审法
> 评审人：Senior UX Lead (AI)

---

## 总体评估

**Rating：⚠️ Needs Improvement**

**Summary：**

本 UX 规格在**角色画像的精细度**和**移动端审批体验**方面做出了扎实的定义。角色导航分割、教育型空状态、自动保存策略等决策方向正确。

但存在一个**根本性的矛盾**未解决：

> 模板设计者被定义为"基础电脑用户"（只会邮件、填表、浏览网页），但设计器被定义为**三栏布局 + 结构树 + 属性面板 + 拖拽编排**的专业工具。

这两者不匹配。如果目标用户是基础电脑用户，当前设计器 UX 复杂度需要大幅降低。如果设计器必须维持当前复杂度，则角色画像需要调整为"Excel 熟练用户"。

此外，以下关键 UX 场景缺失：
- NL 生成失败时的恢复路径
- 设计器键盘可访问性（拖拽的键盘替代方案）
- 模板迁移过程的数据完整性校验 UX
- 审批人在摘要中看不到关键信息时的展开路径

# 关键问题 (Critical Issues)

---

### Issue 1：设计器复杂度与用户技能水平矛盾

```
Issue：      Designer Complexity vs User Skill Mismatch

Location：   §4.1 设计器（三栏布局 + 结构树 + 属性面板），§1.2 用户画像

Problem：
  三栏布局 + 结构树 + 属性面板是一种专业创作工具的交互模式
  （类似 Figma、VS Code、Webflow）。它要求用户理解：
  - "结构树"代表数据层级（抽象概念）
  - "属性面板"中不同字段类型有不同配置项（上下文感知）
  - "拖拽"可用于排序和创建（非标准网页交互）
  
  但目标用户画像描述为"会用邮件、填表、浏览网页"的基础用户。
  这类用户对拖拽操作的完成率只有约 60%（NNGroup 研究数据），
  对层级结构树的理解更差。

User Impact：
  基础用户打开设计器后会感到困惑和焦虑 → 放弃使用 → 求助 IT →
  违背"业务自助化"的核心目标。

Severity：  🔴 Critical

Recommendation：
  方案 A（推荐）：将设计师画像调整为"Excel 熟练用户"或"部门流程管理员"，
  他们至少理解基础的数据组织概念。同时保留 NL 入口作为降低门槛的手段。
  
  方案 B：将三栏布局改为更简单的模式——
  取消结构树，改为直接在预览中点击编辑（WYSIWYG 内联编辑）；
  属性面板改为浮动弹出框而非固定面板；
  组件面板改为"添加字段"按钮弹出菜单。
  
  方案 C：分层设计器体验——
  "简单模式"：NL 生成 → 预览确认 → 发布（无编辑）
  "高级模式"：三栏布局（当前设计，面向有经验的用户）
  用户可随时在两种模式间切换。
```

### Issue 2：NL 生成失败路径未定义

```
Issue：      NL Generation Failure Path Undefined

Location：   §4.2 NL 对话创建界面

Problem：
  NL 对话生成表单是一个 AI 依赖的功能。AI 输出不稳定——
  可能生成错误的字段类型、遗漏用户提到的字段、生成不合理的审批链。
  
  当前设计只覆盖了"快乐路径"（用户描述 → 生成 → 满意），
  没有定义生成结果不符合预期时的处理流程。

User Impact：
  - AI 生成错误字段类型（如"日期范围"被生成为两个独立日期字段）→ 用户不会修改
  - AI 遗漏字段 → 用户不知如何添加
  - AI 生成多余字段 → 用户不知如何删除
  - 这些场景导致用户对系统失去信任，退回求助 IT

Severity：  🔴 Critical

Recommendation：
  在 NL 生成结果页面增加：
  1. 生成结果确认视图：列出所有生成的字段，每个字段有 ✓/✗ 确认按钮
  2. "不满意？"操作：重新生成 / 手动修改 / 从模板开始
  3. 差异高亮：如果用户修改 NL 描述后重新生成，高亮显示变化的字段
  4. 撤销生成：保留生成前的状态，一键回退
```

### Issue 3：结构树的认知门槛

```
Issue：      Structure Tree Requires Abstract Thinking

Location：   §4.1 设计器布局 — 右侧结构树

Problem：
  结构树以层级缩进展示表单结构（章节 → 字段 → 子字段）。
  这引入了"数据层级"这一抽象概念。对于"纸质表单心理模型"的用户，
  表单是平面的、线性的——"姓名、日期、部门、原因"就是一个列表，
  不存在"树"的概念。结构树迫使用户学习一个新的思维模型。

User Impact：
  - 用户不理解为什么要用"树"来展示一个简单的表单
  - 用户可能不会使用章节分组（将 5 个字段全部平铺）
  - 错误地在树中拖拽导致字段嵌套到非预期位置

Severity：  🔴 Critical

Recommendation：
  方案 A：用"字段列表"替代"结构树"——
  一个平面列表，用缩进表示章节归属，但不可任意嵌套。
  拖拽只能调整顺序，章节通过"添加章节按钮"创建。
  
  方案 B：结构树作为可折叠/可隐藏的高级功能——
  默认显示平面列表，高级用户可切换到结构树视图。
  
  方案 C：去掉独立的"结构树"面板——
  预览区中的字段可拖拽排序，层级关系在预览中直观体现。
```

### Issue 4：移动端审批摘要可能遗漏关键决策信息

```
Issue：      Summary-First May Hide Critical Decision Information

Location：   §4.4 移动端审批页

Problem：
  审批摘要自动选择"关键字段"展示（金额、日期、设备类型等）。
  但"关键字段"的定义是启发式的——AI 或规则判断哪些字段最重要。
  
  存在风险：对审批人至关重要的信息未被提取到摘要中。
  例如，一个"数据访问申请"表单的关键信息可能是"数据范围"而非"申请日期"，
  但摘要可能错误地将日期作为关键信息展示。

User Impact：
  审批人基于不完整摘要做出错误决策 → 同意本应拒绝的申请 →
  业务风险（数据泄露、超预算采购等）。

Severity：  🟠 High

Recommendation：
  1. 摘要字段由模板设计者在设计表单时手动标记（"审批摘要字段"配置）
  2. 默认摘要至少包含：提交人、提交时间、所有必填字段的值
  3. 摘要下方始终显示"查看完整表单"链接，且视觉显著
  4. 审批操作按钮区域固定显示"查看完整表单后再决定"提示
```

### Issue 5：拖拽交互对键盘用户不可用

```
Issue：      Drag-and-Drop Is Inaccessible to Keyboard-Only Users

Location：   §4.1 设计器布局 — 拖拽交互，§6.5 可访问性规则

Problem：
  设计器核心编排操作依赖拖拽（@dnd-kit）。虽然 @dnd-kit 提供了
  键盘拖拽支持，但规范中未定义键盘替代方案的具体交互。
  
  此外，组件面板 → 画布/结构树的"拖入创建"在键盘操作下非常困难——
  用户需要理解两步操作：先聚焦源 → 复制 → 聚焦目标 → 粘贴/放下。

User Impact：
  - 键盘用户（运动障碍、偏好键盘操作的用户）无法使用设计器
  - 违反 WCAG 2.1 AA 可访问性标准
  - 可能构成法律合规风险（视部署地区法规而定）

Severity：  🟠 High

Recommendation：
  1. 为每个组件面板项增加"添加"按钮（或双击添加），不依赖拖拽
  2. 结构树每个节点增加"上移/下移"操作按钮（键盘可达）
  3. 支持 Ctrl+C / Ctrl+V 复制粘贴字段
  4. 在可访问性规则章节增加键盘操作的具体定义
```

# 改进建议 (Improvement Suggestions)

---

### Suggestion 1：设计器三栏的视觉层级需要重新平衡

```
Current：
  组件面板(240px) | 实时预览(flex:1) | 结构树+属性(360px)

Problem：
  三栏等比例布局导致信息密度均匀分布，用户注意力分散。
  对于"预览居中为视觉焦点"的设计理念，当前 360px 的右侧面板过宽，
  与 240px 的左侧面板形成不对称的"压迫感"。

Suggested：
  组件面板(200px) | 实时预览(flex:1, min-width: 400px) | 属性(280px)
  
  预览区始终占据最大视觉面积。
  左侧面板在不需要时支持折叠为图标（只显示字段类型图标）。
  右侧属性面板在未选中任何字段时显示空状态引导文案。

Expected Benefit：
  视觉焦点更清晰，预览真正占据中心地位。折叠能力为基础用户
  提供渐进式的界面复杂度——初始只看到预览，需要时才展开工具面板。
```

---

### Suggestion 2：增加 NL → 编辑器过渡动画和引导

```
Current：
  NL 生成后直接进入三栏设计器，无过渡。

Problem：
  NL 对话界面（单栏，居中，对话式）和设计器（三栏，工具式）的
  交互模型完全不同。突然切换造成认知断裂——用户迷茫"我在哪？现在该做什么？"

Suggested：
  NL 生成完成后：
  1. 过渡动画：对话界面缩小移动到左侧面板 → 右侧展开预览和属性
  2. 首次进入设计器的用户看到 3 步引导浮层：
     "① 左侧选择字段类型，点击添加到表单
      ② 中间预览你的表单效果
      ③ 右侧调整字段属性"
  3. 引导可跳过，但保留"帮助"入口

Expected Benefit：
  用户理解两个界面之间的关系，降低从 NL 到编辑器的认知跳跃。
  首次使用引导提高设计器可学习性。
```

---

### Suggestion 3：审批链时间线可视化

```
Current：
  审批链以列表形式展示状态，未定义具体视觉样式。

Problem：
  审批链的"流转感"需要时间线来传达。简单的文字列表（节点1: 已通过 →
  节点2: 审批中）不能直观展示流程进度和当前焦点。

Suggested：
  垂直时间线设计：
  
  ● 节点1：直属上级审批
  │ 李建国 · 已通过 · 2026-08-05 15:00
  │ 意见：同意
  │
  ● 节点2：IT 部门审批         ← 当前节点（高亮 + 脉冲动画）
  │ 待处理
  │
  ○ 节点3：财务审批           ← 未开始（灰色）
  
  当前节点使用主题色 + 左侧粗线 + 微妙呼吸动画
  已完成节点使用绿色圆点 + 对勾
  未开始节点使用灰色空心圆

Expected Benefit：
  审批流程一目了然——谁已完成、谁在处理、谁在等待。
  时间线的垂直流动天然传达"流转"概念。当前节点高亮引导注意力。
```

---

### Suggestion 4：定义"草稿过期"的用户通知策略

```
Current：
  §6.3 "草稿保留期限 2 年，超期自动清除（清除前 7 天通知用户）"

Problem：
  仅提到"通知"，未定义通知渠道和内容。如果用户错过了通知，
  草稿被删除后没有恢复手段，造成数据丢失和用户挫败感。

Suggested：
  过期提醒策略（多阶段）：
  
  T-30 天：站内通知 + "你的草稿将于 30 天后过期"
  T-7 天：站内通知 + 邮件（如已配置）
  T-1 天：站内通知 + 邮件
  T-0：自动清除 + 站内通知："草稿已过期并被清除"
  
  清除后保留宽限期 7 天（软删除），用户可联系管理员恢复。
  7 天后物理删除。

Expected Benefit：
  多次提醒降低草稿意外丢失的概率。软删除提供最后的恢复手段。
```

---

### Suggestion 5：字段类型选择增加引导

```
Current：
  组件面板列出所有字段类型，无优先级或引导。

Problem：
  基础用户面对 13 种字段类型不知道如何选择。
  "文本输入"和"多行文本"的区别？"下拉框"和"单选按钮"的区别？
  这些是 UI 组件的技术差异，而非业务差异。

Suggested：
  组件面板分组增加描述性引导：
  
  基础控件
  ┌ 单行文字  "姓名、编号、标题等短文本"
  ├ 多行文字  "备注、描述、原因等长文本"  
  └ 数字     "金额、数量、分数等数值"
  
  选择控件
  ┌ 下拉选择  "从预设选项中选择（适合 5+ 个选项）"
  ├ 单选按钮  "从预设选项中选择（适合 2-4 个选项）"
  └ 多选      "可选择多个选项"
  
  每个类型带微型图标 + 一行描述。
  
  NL 生成时，AI 自动选择合适类型，用户不需要理解类型差异。

Expected Benefit：
  用户在鼠标悬停或点击组件前就能理解每个类型的用途。
  减少错误选择导致的后续修改。
```

# 缺失考量 (Missing Considerations)

---

### 缺失 1：设计器中的"撤销/重做"交互未定义

```
虽然 §5.4 列出了 Ctrl+Z 快捷键，但没有定义：
- 撤销栈的粒度（每次属性修改一个栈帧？还是批量操作？）
- 撤销操作的视觉反馈（被撤销的变更如何提示）
- 撤销栈的生命周期（关闭浏览器后是否保留？）
- 撤销的上限（最多撤销多少步？）

影响：设计器作为创作工具，撤销/重做是基础交互。未定义会导致
开发团队自行决策，可能出现不一致的实现。
```

---

### 缺失 2：多人协作的冲突处理 UX

```
签出/签入机制假设了独占编辑，但未定义：
- 用户 A 签出编辑中，用户 B 尝试签出 → 提示"已被 XX 签出"之后呢？
  B 是否可以请求 A 签入？可否查看 A 的编辑进度？
- 管理员强制签入后，A 打开浏览器时发现被强制签入 → 什么体验？
  A 的未保存修改如何处理？
- 签出超时（用户下班关机）→ 锁是否自动释放？

影响：独占编辑是协作冲突的"硬"解决方案，但边缘体验未定义。
```

---

### 缺失 3：移动端填写器在弱网环境下的体验

```
移动端审批的弱网体验未定义：
- 审批人在地铁/电梯中打开审批 → 加载超时 → 什么反馈？
- 审批操作提交时网络断开 → 操作是否排队重试？
- 离线填写草稿 → 能否本地保存并在恢复网络后同步？

影响：移动端用户经常处于不稳定网络环境。弱网体验差会导致
用户放弃移动端使用，回归桌面（违背移动优先策略）。
```

---

### 缺失 4：审批超时的用户体验

```
产品规格提到"审批人长时间未处理（如超过 7 天），系统显示'已等待 X 天'"。
但 UX 规格未定义：
- 提交人看到"已等待 7 天"后能做什么？催办？撤回？
- 审批人是否收到超时提醒？
- 是否存在自动升级（超时后跳至下一节点或转交上级）？

影响：提交人的焦虑随等待时间增长。无操作入口导致用户无力感。
```

---

### 缺失 5：模板版本历史对比 UI

```
业务规则要求模板变更不影响已有实例（版本隔离）。但：
- 设计者修改模板后发布 v2 → 是否需要让设计者看到 v1 → v2 的差异？
- 运维导入新版本时 → 是否需要预览新旧版本的变更？
- 填写者打开旧版本草稿时 → 提示"模板已更新"后，如何展示差异？

影响：版本隔离是核心架构特性，但用户侧缺乏版本变更的可见性。
```

---

### 缺失 6：错误日志与用户反馈闭环

```
用户遇到问题后（如 NL 生成了错误的表单、审批流卡住），如何反馈？
- 是否有"报告问题"入口？
- 反馈时是否自动附加上下文（当前模板 ID、操作步骤）？
- 反馈后的追踪机制？

影响：无反馈闭环 → 问题不被发现 → 重复发生 → 用户流失。
```

# 正向发现 (Positive Findings)

---

### ✅ 角色导航分割设计

为不同角色提供完全不同的导航结构是正确的决策。它消除了"为什么我看到这个菜单"的困惑，降低了无关信息的干扰。这是企业级多角色系统的标准优秀实践。

---

### ✅ 教育型空状态

每个空状态都包含三个要素——图标、说明文字、行动指引——而非简单的"无数据"。这在系统上线初期尤其重要，帮助用户建立功能认知。草稿箱空状态的"填写表单时系统会自动保存"文案特别值得肯定——它在教用户功能行为，而非仅告知当前状态。

---

### ✅ 自动保存策略的完整性

双层保存（服务端 30s + 本地实时）的设计考虑了两种风险——网络中断和服务端故障。加上恢复时的横幅提示和浏览器关闭保护，形成了完整的防丢失闭环。这是生产级 UX 的标准。

---

### ✅ 审批操作的分级确认

将"同意"（无确认/可选意见）和"拒绝/退回"（必填原因 + 二次确认）区分对待是正确的。高频低风险操作保持流畅，低频高风险操作增加必要的摩擦。这体现了对审批人心理模型的理解。

---

### ✅ 移动端审批摘要优先策略

摘要卡片将完整表单折叠在"查看完整表单 ▼"后面，尊重了审批人的时间。大多数审批决策可以在看到关键字段后做出，不需要滚动整个表单。

---

### ✅ 预览双模式（静态 + 交互测试）

这个设计很精妙——静态模式用于快速迭代（调属性 → 看效果），交互模式用于深度验证（填数据 → 测联动）。两个独立的状态管理器避免了调试数据污染设计数据。

# 最终建议

## ⚠️ Needs UX Revision

**原因：**

本 UX 规格存在一个**根本性的角色-工具匹配矛盾**，以及 4 个 Critical/High 级别问题需要在进入 UI 视觉设计和前端开发前解决：

1. **必须解决**：设计器复杂度与目标用户技能水平的矛盾（Critical）
2. **必须解决**：NL 生成失败路径（Critical）
3. **必须解决**：结构树对基础用户的认知负担（Critical）
4. **必须解决**：拖拽的键盘可访问性替代方案（High）

**建议在修订中优先处理：**

| 优先级 | 行动 |
|--------|------|
| P0 | 重新校准设计者角色画像 OR 简化设计器交互模式（二选一） |
| P0 | 定义 NL 生成的错误/不满意处理流程 |
| P1 | 增加拖拽的键盘替代方案到可访问性规则 |
| P1 | 定义审批摘要字段的可配置机制 |
| P2 | 完善：撤销/重做 UX、协作冲突 UX、弱网体验、审批超时处理 |

**修订后预期达到：Good 或 Excellent 评级，可以进入视觉设计和前端开发。**
